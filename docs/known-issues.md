# Known Issues and Limitations

1. **Needs internet for NHTSA.** The make and model lists and the live dashboard question need a connection. Without one, the app shows a red message that says what is wrong (no internet, too slow, blocked by a firewall, NHTSA problem) and Make and Model can be typed by hand instead; everything else still works. Results are never cached on purpose.
2. **US market models.** NHTSA lists vehicles sold in the United States, so some models are not sold in the Philippines. Approved by the instructor for this capstone.
3. **The waiting list and the owner's undo are saved, the renter's undo is not.** The waiting line and the check-out history are stored in `WaitingEntry` and `CheckoutLog`, so they survive a restart. A renter's Undo in the Cars tab is still kept in memory (see item 25). Nobody is told when a waiting renter's turn comes: the owner serves the line by hand.
4. **CSV format is simple.** Names with commas or quotes inside are not supported. Bad lines are skipped and listed in the Import tab.
5. **Plate numbers are unique among the vehicles in the fleet.** The database refuses a second vehicle with the same plate (capital letters ignored) with a unique index, `idxVehiclePlate`, and `Database` turns the error into a `DuplicatePlateException`. Add Vehicle, Edit and Restore also check first to show a friendly message. A removed vehicle does not block its plate, so it cannot be restored while another vehicle uses that plate. An old `fleetrent.db` that already holds two vehicles with the same plate cannot build the index; the app then checks the plate before saving, as before.
6. **Dates have no time of day.** A rental is billed in whole days, and a same-day return counts as 1 day.
7. **Dashboard counts only returned rentals.** Ongoing rentals are not in the totals.
8. **One local file.** The data is one local file (`fleetrent.db`) on one computer. The owner and renters log in, and several windows of the app can use the file at the same time on that computer, but there is no server, so renters on other computers cannot connect.
9. **Live dashboard question is slow for many makes.** It makes one API call per make, one after the other.
10. **Car photos need the internet and are not always right.** The photo comes from a Wikipedia search for "make model". Some models have no photo, and a few may show a different car or a logo. The user can press "Choose photo..." to use their own picture, or the app shows the drawn car. We tested the photo code with a fake server, not with live Wikipedia.
11. **Photo files are not in the database.** They are saved in the folder `vehicle_images` next to `fleetrent.db` (named by vehicle id) and are not committed to Git. A new computer starts without photos until the user adds them or presses "Find photos for all".
12. **Utilization uses the whole month.** Fleet utilization divides by every vehicle times every day of the month, even for the current month that is not over yet.
13. **No colors from NHTSA.** The vPIC service has no color data, so the Color box uses a fixed list of 17 names.
14. **Only cars, SUVs and motorcycles.** NHTSA also lists trucks, buses and trailers. FleetRent has only the three types, so those are not offered. NHTSA files SUVs under "mpv" (multipurpose passenger vehicle), so a few vans may show up in the SUV list.
15. **The year is required and starts at 1996.** NHTSA only has model years after 1995, and the vehicle form asks for the year first (no future year), because the model list depends on it. If NHTSA has no model of a make for a year, the list stays empty and the make and model can be typed by hand.
16. **The NHTSA addresses were taken from NHTSA's documentation.** The tests use a fake server; the live service must be checked once on a real computer with internet (see the guide, Part 8).
17. **Rentals from a CSV file are not checked for date overlap with each other.** A new rental made in the Rentals tab is refused while the vehicle is out (the renter joins the waiting list), and a vehicle can be rented again once it is returned. The CSV import saves past history as it is: it checks the plate, the dates and the miles, but not whether two rentals of the same vehicle overlap. The database has no date-overlap rule.
18. **Extra-mile fees are shown as a hint, not in every list.** The fleet list shows the price for 1 day with no extra miles. A hint under the list gives the free miles per day and the fee per extra mile for each type (Sedan 100 free, 0.20; SUV 80 free, 0.30; Motorcycle 60 free, 0.15). The amount to pay (the charge with extra miles plus the late fee) is shown when a rental is returned.
19. **Owner sign-up is open and the database is for one shop.** There is no owner code, so anyone who opens the app can create an owner account, as the project asked (the app is open to every aspiring rental shop owner). Every owner who uses the same `fleetrent.db` sees the same fleet. A real service would give each shop its own database.
20. **Forgot password uses a security question.** The project has no email service, so a password is reset by answering the question chosen at sign up. Anyone who knows the answer can reset the password. After 5 wrong log-in tries in a row a username waits 30 seconds (this wait is kept in memory and resets when the app closes).
21. **Removing a vehicle hides it, it does not delete it.** The row stays in the database (`Vehicle.active = 0`) so old rentals keep their vehicle. A vehicle that is rented out cannot be removed. Its active reservations are cancelled. The owner can bring it back with Removed vehicles, then Restore.
22. **The vehicle type cannot be changed when editing.** The type decides the fee rule, so to change it the owner removes the vehicle and adds a new one.
23. **Booking limits.** A renter can book at most 30 days at a time, and reserve at most 180 days ahead. Rent starts today, and Reserve starts tomorrow or later. These numbers are our rules (`BookingService.MAX_DAYS`, `MAX_DAYS_AHEAD`).
24. **Screens refresh every 3 seconds.** A change made in one window shows in the other window within about 3 seconds, not instantly. Pressing a button always uses the latest data, so two windows cannot book the same days.
25. **A renter's Undo only covers the current session.** The Undo stack is in memory. After sign out or closing the app, the renter cancels a reservation in My bookings instead.
26. **The screen tests need a display.** `ScreenFlowTest` (20 tests) opens real windows for a moment. On a computer with no display (for example a server) they are skipped, not failed, and the other 391 tests still run. Do not touch the mouse or keyboard while they run.
27. **Very small windows scroll.** The window cannot be smaller than 860 x 560. At that size some tabs (Import, Vehicles, My bookings) are wider than the window, so they show scroll bars. From about 1100 pixels wide, everything fits without scrolling.
28. **A long CSV import holds the database for a moment.** The import saves in one step, so another window that saves at the same time waits (up to 5 seconds) until it finishes.
29. **The screens call two helpers of the service package directly.** All the other work goes through the controllers. `Validators` (what may be typed) and `RentalMath` (the price estimate) are pure helpers with no database and no web, so the screens use them without a controller.
30. **A running import cannot be cancelled.** Background jobs run on one shared pool of 4 threads (`Background`). A job can be waited for, but the Import tab has no Cancel button.
31. **A few screen-building methods are a little over 50 lines.** `RentalTab`, `RenterBrowseTab`, `ReservationTab` and `VehicleTab` each have one method that builds a whole form (53 to 59 lines). The rest of the code is shorter. No code line is longer than 100 characters.
32. **The late fee is our own rule.** A rental returned after its end date pays 10 percent of the daily rate for each late day (`RentalMath.LATE_FEE_RATE`). Rentals imported from a CSV file have no saved payment, so their cost is worked out from the days and miles, without a late fee.
33. **The waiting list is not shown to a second window until it reloads.** The line is read from the database each time, so another window sees it after its next refresh (within about 3 seconds).
34. **Some numbers are still plain numbers.** The coordinates of the car drawing in `CarGraphic`, the rows of the demo vehicles in `SampleData` and the column positions in the SQL reading code of `Database` are the picture, the sample data and the table layout themselves, so they are not named one by one.
35. **There is no separate clerk role.** The owner is the manager. Removing or restoring a vehicle and recording maintenance are owner-only, and every other account (renters) is refused.
36. **The login message tells whether the username exists.** The login says "The username is not correct" or "The password is not correct", as the project asked. A real service would use one message so nobody can test which usernames exist. The 5-tries lock still works.
37. **The car photo may not be of the exact year.** The search uses the year, make and model and accepts a Wikipedia page only if its title has both the make and the model, but Wikipedia usually has one picture per model page (often the newest). When no page matches, a drawn car is shown.
38. **The practice CSV has made-up names.** "Create practice CSV" writes a 50,000-row file with random renter names for the dashboard demo. The export from the app does not: it lists only real rentals and leaves a column blank when the value is not known.
39. **The Import history shows at most 2,000 rows of a file at a time.** Every line of every import is saved, but the table is limited so the window stays fast; the choice Saved or Skipped narrows the list.
40. **The login background photo was chosen by the team.** It is a picture of a sports car and a motorcycle used only behind the login card. Its owner's permission must be confirmed before the app is published outside the course.
